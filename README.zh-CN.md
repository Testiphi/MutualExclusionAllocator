# [MutualExclusionAllocator](https://github.com/Testiphi/MutualExclusionAllocator)

[English](README.md) | **中文**

> 🌐 **在线演示**：[testiphi.github.io/MutualExclusionAllocator](https://testiphi.github.io/MutualExclusionAllocator/)

一个用于 Gauntlet 挑战模式的用车分配工具，支持五区/四区、四种数据档位、车辆星级与特殊跑法，输出车辆互斥的 Pareto 最优方案。

---

## 概述

本工具求解的是一个**多组互斥分配问题**：

- 你有一个**资源池**（例如物品、代理、资产），每个资源有「可用」与「不可用」两种状态。
- 你定义至多 **N 个分配组**，每组带一个**按优先级排序的候选子集列表**。
- 每个候选子集包含一个或多个资源，它们在该槽位上**互相可替换**。
- 一个资源被分配到某个槽位后，**不能再被其它槽位复用**。
- 部分条目可能有**替代路线**，产生不同的效率指标，可按槽位单独启用。

算法通过**回溯枚举**遍历全部可行分配，在叶子处增量维护 **Pareto 非支配前沿**，只返回那些在所有维度上都无法被严格改进的方案。

## 算法

### 1. 数据模型

每个轨道（分配槽位）持有一组**条目组**。组内资源互相可替换 —— 任选其一即可在该优先级上满足该槽位。

```
槽位: "Slot A"
  组 0: {资源 X, 资源 Y}  ← 优先级 0（最优）
  组 1: {资源 Z}           ← 优先级 1
  组 2: {资源 W}           ← 优先级 2
  ...
```

部分条目带有 `sc`（特殊／启发式路线）标记，必须带合法 `sc_type`。启用时普通与特殊跑法一起参与比较，同车取有效成绩更快的一条，再按成绩排序候选。

### 2. 回溯枚举

```
for 每个槽位（按顺序）:
  ① 留空该槽位 → 递归进入下一槽位
  ② for 每个条目组（按优先级升序）:
       for 组内每个资源:
         if 该资源未被占用 AND 可用:
           分配 → 递归进入下一槽位
```

**留空本身也是一条可行方案**（允许部分分配），因此每个槽位都会显式枚举「留空」分支：
某槽位可用的资源，留给后面的槽位可能更划算，两个方案优先级向量不同、互不支配。

> 若只在「本槽位已无资源可分」时才留空，靠前的槽位会对稀缺资源获得**绝对优先权**，
> 并静默漏掉一批非支配方案（例：两个槽位都只能选资源 A 时，`[空, A]` 从未被枚举）。
> 留空的代价是哨兵值（见下），因此在资源充足时它总会被支配、不会出现在前沿里。

### 3. Pareto 非支配过滤

每个完整分配产生一个**优先级向量** `[p₀, p₁, ..., pₙ₋₁]`，其中 `pᵢ` 是分配给槽位 `i` 的资源的优先级（**越小越好**）。未分配的槽位取哨兵值。

**方案 A 支配方案 B**，当且仅当 `∀i : A[i] ≤ B[i]` 且 `∃j : A[j] < B[j]`。

每个叶子方案立即与当前前沿比较：被支配则丢弃，否则移除它支配的方案并加入前沿。
相同向量的不同车辆分配全部保留。搜索结束后按优先级总和、向量字典序排序，再返回至多 25 个方案。
这里优化的是各图的候选排名，不直接最小化所有赛道的总耗时。

## 档位

系统支持多个数据档位以适配不同用途：

| 档位 | 用途 |
|------|------|
| **理论** | 含已知最优效率指标的参考数据，包含启发式路线成绩。 |
| **高手** | 实战数据，含逐项效率分数与可选星级。 |
| **普通** | 高手档的子集，排除特定条目（黑名单），不含分数。 |
| **自动** | 白名单模式 —— 仅一组精选条目可用。 |

各档位共享同一套槽位结构，但在「哪些条目可用」与「条目内哪些资源可用」上不同。切换档位会重建分配索引，但不改变底层算法。

---

## 启发式路线（特殊路线）

部分槽位的条目可能带 `sc: true` 标记，代表不同的操作方式（例如不同技巧、捷径、取巧手段），产生不同的效率指标。

- **按槽位独立开关**：每条启发式路线可单独启用或停用。
- **三态控制**：`全部`（默认）/ `指定跑法` / `关闭`。关闭时剔除该槽位全部 `sc` 条目；
  指定跑法时只保留该类型的 SC，普通跑法仍参与比较。
- **同车合并**：普通与允许的 SC 成绩一起比较，每辆车仅生成一个候选，取有效成绩较快者。
  切换跑法会重新排序候选，普通成绩本身不变，但车辆的优先级名次可能变化。
- **独立估算**：高手档按普通跑法和各个 `sc_type` 分别插值/外推，再取最快成绩；不同特殊跑法之间不混合插值。显示与排序使用同一计算入口。
- **影响范围**：既影响分配次序（算法先尝试哪些资源），也影响展示的效率分数。
- `sc_type` 的取值必须在 `repo/data_tools.py` 的 `SC_TYPES` 白名单内（共 9 种），
  新增跑法类型须先在该常量登记。

## 双区模式

每个槽位可持有两套独立的优先级列表（例如「A 区」与「B 区」）。用户在两个区之间切换；切换时会相应过滤候选列表与资源池。

本项目对应五区与四区；车池和星级规则由 `cars.json` 的 `zones` / `star_rule` 指定，前端与 Python 校验共用。
四区特改车的星级上限由人工指定，不能只凭满改性能分超过 4200 判断其违规。

## 数据格式

`gauntlet_data.json`（赛道数据）与 `cars.json`（车辆库，同时承载规则）都是本项目的实际文件，
字段名固定为中文，下面是真实结构（节选自实际文件）：

```json
// gauntlet_data.json
{
  "_version": 1,
  "_comment": "...",
  "tier_info": { "理论": { "label": "...", "desc": "..." } },
  "tracks": [
    {
      "大地图": "古老斗技场",
      "小地图": "偏僻小道",
      "has_special_route": true,
      "special_route_note": "...",
      "五区": {
        "理论": [ { "cars": [ { "name": "9x8" } ], "time": 16.9,
                    "sc": true, "sc_type": "跳图" } ],
        "高手": [ { "cars": [ { "name": "r兔", "stars": 6 } ], "time": 18.59 } ],
        "普通": [ { "cars": [ { "name": "r兔", "stars": 6 } ] } ],
        "自动": [ { "cars": [ { "name": "白龙" } ] } ]
      },
      "四区": { "理论": [], "高手": [], "普通": [], "自动": [] }
    }
  ]
}
```

### 条目属性

| 字段 | 类型 | 说明 |
|------|------|------|
| `cars` | `[{name, ?stars}]` | 候选资源；本工具恒为单元素数组（一组一辆） |
| `time` | number / null / 缺失 | 有成绩时为正有限秒数，越小越好；null 或缺失表示无成绩 |
| `sc` | bool | 标记为启发式路线条目 |
| `sc_type` | string | 启发式跑法类型，须属于 `data_tools.SC_TYPES` |

理论/高手档按 `time` 升序排列，无成绩的条目排末尾；普通/自动档只表示「可用」（不需要 `time`）。
当前维护约定是理论/高手有成绩才建条目，不预建无成绩占位；工具仍兼容已有无成绩条目。
仅**非 SC 高手条目**必须有同车同星的普通档镜像（校验强制）；SC 只存在于理论/高手档，不补普通镜像。
每张赛道必须显式包含两区及各自四个档位，档位可以是空列表。

```json
// cars.json
{
  "_comment": "...",
  "_nickname_map": { "007s": "Glickenhaus 007S" },
  "cars": [
    {
      "title": "W Motors Lykan Hypersport",
      "nickname": "狼崽",
      "score": 4083, "class": "S", "max_stars": 5,
      "max_speed": 407.6, "acceleration": 80.48, "handling": 40.97, "nitro": 58.46,
      "zones": ["五区", "四区"],
      "star_rule": { "min": 5, "max": 5, "default": 5 }
    }
  ]
}
```

`nickname` 是数据文件里引用这辆车时使用的名字；`zones` 与 `star_rule` 是**人工指定**的车池与星级规则，
前端与 Python 校验共用它们（见下文「架构」）。

## 架构

纯客户端静态应用：

```
config.js → app_state.js → api.js → index.html（状态、候选准备、渲染）
                         ├→ allocator.js（纯分配算法）
                         └→ race_scores.js（成绩计算）
```

- **Config** —— 路径、键名、存储设置
- **数据加载层** —— 当前静态模式加载 JSON；API 模式是预留接口，仓库没有后端实现
- **规则派生** —— 车池（`zones`）与星级规则（`star_rule`）从 `cars.json` 派生，
  见 `index.html` 的 `buildCarRules()`；**这是规则的唯一来源**，页面里不再有硬编码副本
- **应用逻辑** —— 准备候选、估算星级成绩、管理状态并渲染界面
- **算法模块** —— `allocator.js` 无 DOM/网络依赖，回溯时增量维护 Pareto 前沿
- **成绩模块** —— `race_scores.js` 无 DOM/网络依赖，管理星级曲线和独立跑法估算；四区空候选保持为空，不借用五区列表
- **状态边界** —— `app_state.js` 校验车库/跑法状态，只允许最新排队计算发布结果；保存失败在页面提示，损坏车库在启动时不被覆盖
- **状态持久化** —— 车库、星级与界面偏好保存至当前浏览器的 localStorage；没有账号或跨设备同步
- **本地维护** —— Python 工具维护 JSON/Excel，不参与网页运行

无需服务器、无构建步骤、无数据库。

> **规则的单一来源**：车池与星级规则原先硬编码在 `index.html`，Python 侧另有一份简化表
> （`data_tools.ZONE4_MAX`），两侧已经分叉（前端 72 车有规则，Python 只认识 15 车，且从不校验最低星级）。
> 现在统一到 `cars.json` 的 `zones` / `star_rule`，前端与 `python validate_data.py` 读同一份定义。
> 改车辆规则请改 `cars.json`。

## 开发

### 数据处理流水线

安装、路径、审核步骤与恢复方式见 [Python 维护工具](PYTHON_TOOLS.md)。

1. 导出一份独立基准：`python export_xlsx.py --output baseline.xlsx`。
2. 生成键控审核清单：`python diff_xlsx.py --base baseline.xlsx --user user.xlsx --output changes.review.json`。
3. 逐条审核；仅对已批准的条目把 `accepted` 置为 `true`。
4. 预检：`python apply_changes.py --review changes.review.json`；用 `--output` 可单独输出预览。
5. 用 `--write` 应用，运行 `python validate_data.py`，然后重新导出并比对。

既有目标文件在原子替换前会先备份。历史带日期的脚本与用户表格备份**已清理，不在本地保留**——追溯请用 git 提交历史。
每张赛道必须显式包含两区及各自四档，空列表合法；SC 只允许理论/高手档。
同步仍以性能分上限为门槛，同时要求双区车池归属与两区星级合规；不适用条目列出原因并跳过，已有违规仍阻止同步。

四五区同步先运行 `python sync_zones.py` 查看预检；确认清单后才加 `--write`。
两区不同成绩取更快值，写入前复核源文件是否变化，避免覆盖处理中发生的修改；这不提供多进程文件锁。

### 算法说明

- 叶子数上界为 `O((k+1)^n)`（含留空），每个叶子还需扫描前沿；前沿很大时比较成本和内存仍会增长。
- 当前在回溯叶子处维护前沿，被支配的方案直接丢弃，只有进入前沿的方案才复制数组。
  相同向量的不同车辆分配全部保留；搜索期不截断，全部枚举结束后才排序并返回至多 25 个。
- **性能对比（2026-10-01，Node v24.15.0 / Windows x64 / i9-13900H / 63.6 GB 内存）**：

  | 区/档 | 去重后候选数 | 枚举叶子 | 耗时旧→新(ms) | 调用前后堆差值旧→新(MB) |
  |---|---|---|---|---|
  | 五区/理论 | 22/18/18/18/18 | 2,347,041 | 517.6→150.1 | 631.8→0.6 |
  | 五区/高手 | 20/12/11/11/10 | 309,414 | 74.0→23.2 | 88.9→1.0 |
  | 四区/理论 | 12/12/11/10/10 | 186,020 | 46.9→14.6 | 56.3→2.0 |
  | 四区/高手 | 9/8/7/7/7 | 31,404 | 9.6→4.8 | 10.8→2.0 |

  新旧分别在独立进程冷调用一次，参数 `--expose-gc --max-old-space-size=8192`。
  输入取各区档去重后候选最多的五张图、分区满车库、SC 全开、默认星级；高手档使用前端原函数估算成绩。
  计时仅包住求解调用，叶子计数另跑；调用前 GC、调用后不 GC。**堆差值不是峰值或分配总量**，期间可能发生 GC。
  旧版取 `ce30445` 的算法。旧报告把同车多星/多跑法重复当作候选，新口径已对齐页面，绝对值不能直接与旧报告比较。
  这是密集输入样例，不是所有组合的最坏情况证明，也不是重复测量的统计结论。
- 求解仍同步运行在浏览器主线程，`requestAnimationFrame` + `setTimeout` 只延后开始。
  **尚未做浏览器端压力测试**；Node 数字不含页面渲染，不代表浏览器或移动设备耗时。
- 部分分配：任何一个槽位都可以留空，留空与其他分支一样被显式枚举；
  留空取哨兵值（99），故资源充足时留空方案一律被支配，不会出现在前沿里。
- `SCHEME_LIMIT` 只限制**返回/显示**的方案数，不限制枚举量或搜索期前沿大小。
