## 原因与证据

切换入口通过链接整页导航，每次会读取脚本、样式、成绩及账号状态。旧Nginx模板对整个server使用同一每IP 5r/s、burst=30限流，包括api.js、国际服三个JSON和国服`/api/scores/snapshot`。频繁导航耗尽额度后，脚本429会使`api`未定义，数据429会产生对应加载失败；桶恢复后可重新打开。这是经本地真实Nginx复现的配置问题，不是已确认的双服状态串用竞态。构包时尚未读取生产配置与日志；本轮后续已由用户回传确认同一旧zone拦截启动资源，详见上方验收。

本地Nginx 1.26.3、环回地址独立端口、无账号的假接口对照：相同78次启动资源请求，旧模板33次200、45次429；新模板78次200。新模板下连续登录POST、公开路径POST和管理员GET仍能触发429；受保护桶耗尽时api.js及成绩快照仍可读取。两套配置`nginx -t`通过。测试进程均已停止；此验证不是Ubuntu生产Nginx版本的验收。

## 修改

- `production/nginx-rate.conf`使用按方法/路径选择的key，公开页面资源及明确列出的启动只读接口不消耗业务接口额度。其余请求仍按IP限流。
- `production/nginx-https-location.conf`使用新zone名`racepick_api_requests`，避免沿用不同key的旧共享内存区。需成套更新两份配置。
- `api.js`仅对成绩启动GET的429/503有限重试，优先遵守不超过5秒的Retry-After；默认等待1秒、2秒，最多3次请求。写入请求从不重放；404、哈希错误、版本混用仍直接失败。
- 同一页并发读取复用同一快照。国服失败Promise会被清除，之后可再次加载；国际服仍校验原始字节和版本，不回退国服。
- 页面缺少api脚本时提供明确提示；普通在线错误不再一律误提示“请通过HTTP打开”。
