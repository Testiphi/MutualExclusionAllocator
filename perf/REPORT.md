## 测量口径与结果限制

Node v24.15.0 / Windows x64 / i9-13900H；浏览器为 Codex 内置 Chromium 155 / Windows x64，报告逻辑并发数 20。没有手机或 CPU 降速模拟。Chrome 扩展入口不可用，故用内置浏览器，不能把结果标为独立 Chrome 或移动浏览器。

改造前先单独生成 baseline-node.json，之后新旧在同进程使用同一批输入对比。每例分别记录首次调用，随后每实现 2 次预热，7 次交替实现顺序的测量；不是独立进程的多次冷启动，后续样例的 JIT 可能已预热。计时仅包含同步求解，不含候选准备和结果渲染。Node 每次计时前显式 GC；浏览器不强制 GC。每次对照有序返回结果，但其比较位于计时之外。完整前沿验证由独立测试完成。

初始五区密集输入 Node 首次旧/新 143.812/31.759 ms，重复范围 141.942–176.246 / 30.834–38.180 ms；浏览器首次 124.6/26.7 ms，重复范围 111.0–113.1 / 21.7–23.1 ms。初始中位约快 4.6 倍和 5.0 倍。集成后五区 Node/浏览器约快 4.5/4.9 倍，四区密集 Node 约快 78 倍；浏览器新值已接近计时分辨率，不计算夸大的精确倍数。

普通小输入 Node 约慢 0.012/0.019 ms，单组仅 7 次、绝对耗时很小，不作统计显著性判断。下界检查不是免费：小树或互不支配的大前沿会产生开销，最坏情况仍指数搜索且可能更慢。

Node 保存调用后减调用前的 heapUsed 差值，既非峰值也非分配总量，调用内可发生 GC。例如五区密集首次堆差旧 2,315,952、新 3,130,392 字节，不能据此声称峰值内存改善。浏览器没有堆或峰值测量。零毫秒表示计时分辨率下不可分辨，不是无成本。

浏览器在同步调用前排定定时器：初始五区密集重复延迟旧 111.1–113.2、新 21.7–23.1 ms；集成后旧 112.0–117.1、新 22.4–27.2 ms。小输入定时器自身约 4–6 ms。初始 Long Task 观察器记录 10 个 111–124 ms 长任务，集成后 10 个 111–121 ms，与旧密集调用数量/耗时一致，但未逐任务打标签归因。该结果说明旧算法有明显主线程阻塞；不是完整生产 UI 的输入响应测试。初始 browser JSON 为页面 DOM 读数保留到 0.001 ms；集成后 JSON 为页面下载的完整原始记录。

## 正确性依据与额外成本

对深度 idx 的分支定义下界 L：前 idx 维用当前真实分配优先级；每个未完成位置取 `min(noCarPriority, 所有拥有候选的优先级)`，缺失优先级沿用 noCarPriority。不扣除已使用车辆，放松互斥约束，因此任意可行后代 x 都有逐维 `L <= x`。留空可能优于候选，所以必须纳入 min。

仅当当前某个前沿向量 p 对 L 各维不差且至少一维严格更优时剪枝。因此 `p <= L <= x` 且严格改善维仍严格，p 严格支配全部后代。即使 p 后续被 q 替换，由支配传递性 q 仍支配这些后代。被跳过的叶子在原实现中也会被拒绝，不能增删前沿；未剪枝叶子的访问顺序及前沿更新顺序不变，故最终稳定排序、同分顺序及 slice 行为相同。相等下界不剪，120 个同向量不同分配完整保留；没有搜索期 25 个上限或总分剪枝。

仍先留空、再原候选组/组内顺序；仅在非根非叶节点检查。非有限数值禁用剪枝，沿用参考枚举行为。预计算 O(候选数)，额外空间 O(图数)；每个访问的内部节点最坏 O(当前前沿大小 × 图数)。静态下界可重复使用，代价小但会漏剪因车辆冲突而实际更差的分支，正确性不受影响。

独立插桩副本仅统计搜索成本，不参与耗时测量：五区密集叶子 2,347,041→220,961，额外 615,385 次前沿下界比较、2,636,493 次维度比较；四区密集叶子 194,400→212，额外 365 次前沿比较、1,190 次维度比较。全部计数见 search-cost.json。

## Worker 评估（仅方案，未实施）

旧算法浏览器密集输入已超过 100 ms 并出现长任务，具备提出 Worker 的实测依据。剪枝后桌面约 23.4 ms 仍超过一帧预算，但本组未观察到对应的 50 ms 长任务；先保留本轮小范围修改，是否投入 Worker 由手机实测和用户后续决定。

若实施：页面仍完成去重、星级和 SC 候选准备，发送带 requestId 的不可变快照（groups、优先级键值对、owned 数组、limit、noCarPriority），Worker 重建 Map/Set 调 allocator，回传紧凑方案。数组通信便于未来适配；须单独测序列化、复制与启动成本，小任务可能得不偿失。

取消：requestId 丢弃过期返回仅防止旧结果展示，不中断同步搜索；要立即停算需 terminate 并重建 Worker。发送 cancel 消息不能打断正在执行的同步函数；分片协作取消会增加另一轮算法/调度改造。错误：处理初始化失败、onerror/messageerror 与任务异常；携带 requestId 恢复加载状态并显示错误，不静默吞错或无限重试。

部署预期增加 allocator_worker.js，并改 index.html/app_state.js 的接线、错误与生命周期测试，更新九文件发布清单及校验；API/config 是否需要 Worker URL 配置需实施时决定。算法仍共用 allocator.js，必须保证缓存版本匹配。未来微信小程序需使用其 Worker 路径、打包及消息接口，重新接 UI、存储和生命周期；本轮未验证小程序环境，不承诺零成本迁移，也不涉及框架重写。
